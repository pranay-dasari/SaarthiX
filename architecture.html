03 Runtime data flows

🗣️ Flow A — "Explain this page in Kannada"

User taps mic, speaks. Module 4 · Saarika → transcript + detected language.
Orchestrator asks Module 1 to scrape the active tab → clean pageText.
Module 2 · Sarvam-M summarizes pageText, output constrained to lang=kn-IN.
Module 3 · Bulbul speaks the explanation; transcript also shown in the panel.

📝 Flow B — "Help me fill this form"

Module 1 returns the fields[] map (label, type, selector).
Module 6 + Sarvam-M maps each field to a value from Module 5 (memory); flags missing[].
For each missing field, Orchestrator asks by voice (Bulbul) → user answers (Saarika) → stored to memory.
Module 6 injects values into the DOM and fires input/change events so the site validates them.
Panel shows a review list; user confirms before anything is submitted.

04 Memory decision — local vs cloud

✅ Recommendation: Local, encrypted vault no backend

Store the user profile in IndexedDB, encrypted with the browser's Web Crypto API (AES-256-GCM), key derived from a user PIN via PBKDF2. Data never leaves the device.

Why local wins for this build: ① The data is sensitive (income, Aadhaar-style, bank) — "it never leaves your phone" is a strong pitch & trust story. ② Zero backend = zero auth/server work in a 5-hour window. ③ Lower latency, works offline for reads. ④ Encryption is ~40 lines with native APIs.

Choose cloud only if you need cross-device sync or a shared family profile — then use Supabase/Firebase with per-user row encryption. Not worth it today.

Hackathon path: ship local encrypted now; keep the memory contract (get/set) storage-agnostic so a cloud adapter can drop in later without touching other modules.
