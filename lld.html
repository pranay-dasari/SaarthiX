00 Shared foundation — agree on this in the first 15 min

Everything below is glued by one message envelope and one language code type. Every message is request/response with a reqId. The background worker is the only hub — the panel and content script never talk to each other directly, and only the worker holds the Sarvam key.

02 The stitch — orchestrator glue (worker, Builder B owns)

This is where all three plug in. It is the only place that calls A, B, and C together. If everyone honors the seams above, this function works the moment the stubs are swapped for real code.

// background/worker.js
async function handleUserVoice({ audioBase64, mime }, tabId) {
  send(STATE, { status: "listening" })
  const { transcript, lang } = await C.stt({ audioBase64, mime })      // SEAM 3

  send(STATE, { status: "thinking" })
  const page = await A.scrapePage(tabId)                             // SEAM 1
  const { replyText } = await B.understand({                          // SEAM 2
      pageText: page.pageText, lang, mode: "qa", question: transcript })

  send(STATE, { status: "speaking" })
  const { audioBase64: out } = await C.tts({ text: replyText, lang })  // SEAM 3

  send(BOT_REPLY, { transcript, replyText, audioBase64: out, lang })     // → Panel (C renders)
  send(STATE, { status: "idle" })
}
Read the data path: C(audio→text) → A(scrape) → B(understand) → C(text→audio) → C(render). Each arrow is one seam. Nobody reaches inside anyone else's module.

03 Builder A — Extension shell + Scraping saffron

Files: manifest.json · background/worker.js (router + messaging skeleton) · content/reader.js · panel wiring

  1. manifest.json — permissions: activeTab, scripting, sidePanel, storage; register worker, content script, side panel.
  2. Message router in worker: chrome.runtime.onMessage switch on type, dispatch by reqId, reply {ok,data}. (This is the backbone B & C plug into.)
  3. content/reader.js — on SCRAPE: run new Readability(document.cloneNode(true)).parse() → map to PageDoc. Strip scripts/nav; cap pageText at ~8k chars for the LLM.
  4. Field map (used later for form-fill): querySelectorAll('input,select,textarea') → build stable selectors + nearest-label text.

04 Builder B — Brain / Understanding + sarvamClient cyan

Files: lib/sarvamClient.js · brain/understand.js · orchestrator in worker

  1. lib/sarvamClient.js — one wrapper: chat(messages,lang), translate(text,to) (+ later stt/tts C fills in). Reads key from a single config; centralize URLs. Confirm exact Sarvam routes/payloads from docs first.
  2. brain/understand.js — build prompt: system = "explain webpage content simply for a low-literacy user; answer ONLY in {lang}; ground strictly in PAGE_TEXT." user = pageText + question. Call chat().
  3. If pageText not in target lang, rely on Sarvam-M's multilingual output (no separate Mayura call unless quality is poor).
  4. Orchestrator (the stitch in §02) — owns the STATE machine + sequencing.

05 Builder C — Voice (STT/TTS) + Panel UI violet

Files: panel/index.html · panel/panel.js · voice/stt.js · voice/tts.js

  1. Panel UI — mic button, live transcript area, language picker, "Explain page" button, status pill (listening/thinking/speaking), audio element.
